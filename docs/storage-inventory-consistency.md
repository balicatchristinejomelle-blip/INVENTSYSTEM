# Final frontend storage, inventory state and UI consistency

Standalone update from `76747c5`, on `frontend-storage-inventory-consistency`. The user authorizes commit, push and merge. Existing frontend architecture, physical identifiers, master values and unrelated workflows are retained; there are no backend/database changes.

## Required report

1. **Existing storage model:** Physical FinishedGood records already contained storage/current location, storage and quality flags, source relationships and location history. However, Production selected purpose/location from hard-coded lists; the Owner location master did not drive those confirmations.
2. **Existing bucket model:** Status, availableQty, reservedQty, customer reservation fields and inventoryPurpose overlapped. MO output could carry a Reserved quantity while its physical storage also counted as Temporary. Loaded was not a separate quantity model.
3. **Counting issues:** Production completion/storage status, source versus allocation, Reserved versus Temporary, and ready-stage reserved snapshots could disagree. Reservation movements used negative quantities that the stock-card UI interpreted as Stock Out. Report pages used different direct-field/status counts.
4. **Files modified:** Core: `src/finishedGoodsInventory.ts` (new), `finishedPipeRelations.ts`, `productionGroups.ts`, `store.tsx`, `types.ts`, `App.tsx`, `index.css`. Components: new `FinishedPipeStorage.tsx`, `StoragePurposeFilter.tsx`, `FinishedGoodsMetrics.tsx`; updated `FinishedPipeDetails.tsx`, `BatchTraceability.tsx`. Pages: Accounting Dashboard, Reports, Transactions; Management Dashboard, Operations, Reports, Settings; Marketing Dashboard, FinishedGoods, Orders, Reports; Owner Dashboard, Records, Reports; Plant Manager Dashboard, FinishedGoods, Reports; Production BarcodeScanner, FinishedPipes. Tooling: `package.json`, new `scripts/check-storage-inventory.mjs`, `storage-inventory-baseline.mjs`, and updated grade/pipe/group/reprint regression scripts. This report is also added.
5. **Storage Purpose:** Exactly Inventory Storage for Stock Replenishment and Temporary Storage for Customer Order / MO. Derived from production source, not subsequent allocation. Replenishment reservation retains its original purpose/group. Unresolved source is displayed as an unresolved condition, never offered as a third purpose.
6. **Location validation:** Shared master/type compatibility, active status and Branch Plant checks gate new confirmations and movements. Replenishment confirmation only offers inventory locations; MO confirmation only offers temporary locations. Ready staging is offered for allocated stored pipes during internal movement. Purpose is never a selectable operator field. Existing saved location masters are retained; if no compatible location is configured, Owner must add one in Settings. Defaults include the previously used inventory/staging names, plus a temporary bay; no pipe is moved merely by adding those definitions. Unknown legacy locations/history are preserved but cannot grant unverified availability.
7. **Available:** Requires Quality Pass, confirmed compatible physical storage, replenishment source, and no customer allocation/reservation. Completion alone never makes new production available. Marketing stock checks and new order/reservation callbacks use this shared eligibility calculation.
8. **On Hand:** Uses one shared physical-state calculation and deduplicates permanent physical barcode identity. Available, Reserved, Temporary and Ready are exclusive. Awaiting Storage/Quality Pending records are also still physically held; retained rejected physical pipe records remain held in a separate Rejected state until the existing reject/recycling workflow disposes of them. Those states are not silently lost from physical company holdings. Shipped records leave On Hand. Thus, the four stored-good buckets sum to On Hand only when there are no awaiting/quality/rejected physical records.
9. **Allocation versus bucket:** Customer ownership/reservation references remain separate from bucket quantities. MO source inherently resolves its original order/buyer. Storage confirmation does not reserve again or increment order allocation totals. The actual 100-pipe mixed-order fixture allocates 30 existing pipes plus 70 MO pipes while retaining distinct source/bucket histories.
10. **Reserved versus Temporary:** Reserved is allocated general replenishment inventory. MO stored buyer-specific pipes count as Temporary, not also Reserved. Ready pipes no longer retain an additive Reserved quantity snapshot. The tested mixed result is 30 Reserved + 70 Temporary = 100 unique On Hand.
11. **Loaded:** Optional fulfillmentStatus, not an additive bucket. Production can confirm Loaded for a Ready pipe through its details. It remains Ready and On Hand until actual release. Repeating loading does not add movements or quantities.
12. **Internal movements:** Plant Manager confirms compatible FG locations with a reason. Same-location moves, incompatible locations, unconfirmed/quality-ineligible/released pipes, and unauthorized roles are rejected. Relocation/ready staging retain identity, origin and company quantity, with zero-delta movement history. Existing pellet movement behavior is unchanged.
13. **Stock Out:** Actual authorized shipment/release removes one pipe from On Hand. Reservation, storage, relocation, Ready and Loaded do not. Release can safely resolve a historical MO pipe's originating order when older reservation ID fields are absent; it does not assign another buyer. Repeat release is rejected.
14. **Stock Card:** Good production output is the single authoritative FG Stock In. Production transactions retain their original production totals/material accounting and separately expose quality-pass finishedGoodsQuantity. Storage confirmation is zero delta. The reader classifies old reservation/storage movements as internal without rewriting historical transactions. Loaded/Ready/internal moves have zero Stock In and Stock Out. Opening balance is inferred from retained physical records and recorded movements; inconsistent/partial historical samples display a reconciliation warning rather than fabricating or rewriting history.
15. **Low stock:** Exact-specification Available General Inventory is used by stock targets and replenishment suggestions, not physical On Hand. 0 Available + 100 buyer-specific Temporary remains Out of Stock. Existing minimum thresholds, matching active-PO duplicate prevention, View PO actions, and replenishment formulas remain intact.
16. **Origin Group:** Existing valid MO/Replenishment origin references are preserved through reservation, storage, Loaded, shipment and refresh. Current buyer allocation never becomes a new manufacturing origin. New replenishment output has no MO reference/customer/buyer fabricated.
17. **Quality/status:** Shared priority rules prevent shipped/rejected/pending-quality/MO stock from being Available. Quality Pass with stale Quality Pending status progresses to Awaiting Storage or an evidenced stored state. Shipping takes precedence over stale available/temporary flags. Rejected output still uses the existing reject/recycling material workflow.
18. **Hydration:** Idempotently derives missing source relationships and repairs bucket snapshots from retained records. Does not regenerate identity, barcode, item code, batch, valid origin, physical history, print state or sample quantities. No localStorage clear or data reset is introduced. The existing five MO pipes and one replenishment sample remain intact. Existing valid master entries are not silently replaced.
19. **Spacing:** Added a scoped operational-content variant on existing main content, with 10px section/grid gaps, compact existing cards, normal-height search, balanced filter rows and small natural-flow action separation. Comparable legacy Accounting/Marketing report/dashboard and Production roots reuse page-stack instead of larger inline column gaps. Sidebar, auth and print layouts remain outside this variant.
20. **Center alignment:** Operational cards/headings/labels, inputs/search text, selected values/options, tables including formerly inline-right-aligned numeric/action cells, buttons/actions, empty states and pagination use shared scoped centering. Combobox input padding is balanced around existing action icons. Existing typography/fonts and theme variables remain in use; no global wildcard centering/zero-spacing reset is added.
21. **Six roles:** Real representative pages and complete app shells render for Owner, Accounting, Marketing, Management, Plant Manager and Production. Tests enforce PM-only FG storage/movement and Production-only loading/release; no new roles or sidebar permissions were introduced. Production's scanner storage mode now inspects read-only source-derived purpose; manual storage-purpose/customer/location controls are removed. The unreachable Production RecordStorageModal, which only displayed success without changing records, is removed rather than retained as a false storage confirmation.
22. **Desktop:** Shared source/CSS checks confirm full-row search, four product filter columns, compact balanced operational filters and natural-flow actions. No interactive visual verification was possible.
23. **Tablet:** Existing two-column product breakpoints are preserved; comparable toolbars also use two columns, with full-row search. Static/SSR checks only; no interactive visual verification.
24. **Mobile:** Existing one-column master filters and viewport-safe searchable menu implementation are preserved, with full-width actions at small widths and compact scrolling tables. Visual checks at 360/375/390/412/430px and Light/Dark Mode remain **unverified**: computer-use inventory returned no available apps or browsers. Source preservation/SSR is not visual proof of no overflow or clipping.
25. **Build:** `pnpm.cmd exec tsc --noEmit` and `pnpm.cmd build` pass. No dependency or toolchain changes.
26. **Dev server:** Existing Vite server on port 8443 returns HTTP 200 for `/`, the new inventory helper, Plant Manager FinishedGoods and Production BarcodeScanner modules. No duplicate server was started; this checks running development/module delivery, not a fresh-start test.

Exact baseline checks protect all unrelated store declarations and production material/recipe/reject/recycling arithmetic.
